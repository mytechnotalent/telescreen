## 33.1 What "stripped" actually costs you

When a compiler builds a program, it also records a **symbol table**: a list of
pairs like

```
0x401d80   crc32_le
0x4016f0   aead_seal
```

`strip` deletes that table. The instructions are unchanged; only the names are
gone. So Ghidra, looking at the bytes, can only guess and prints:

```
FUN_00401e00
```

Your job is to decide that `FUN_00401e00` is `crc32_le`, and to be able to
**prove it**. There are exactly four ways to prove it in this binary; we call
them **R1-R4**.

---

## 33.2 The four resolution rules (memorise these)

**R1 - Exact address match against an unstripped twin.**
If you also have the same program built *without* stripping, its symbol table
tells you every name directly. Addresses do not change when you strip, so a name
at `0x401d80` in the twin is the name of `FUN_00401e00`. This is *certain*.
The instructor's answer key is `firmware/teled.unstripped`.

**R2 - Import thunks.**
When the program calls a function from a shared library (OpenSSL, the C library),
the call goes through a small stub called a **PLT entry**. The stub is named after
the library function, e.g. `EVP_EncryptUpdate@plt`. Even in a stripped binary the
*imported* names survive (they must, so the loader can find them), so any code
that calls `EVP_EncryptUpdate` is doing AES-GCM encryption. This is *certain*.
Find them with:

```bash
readelf -rW firmware/teled.stripped | grep JUMP_SLOT
```

**R3 - The PLT0 resolver.**
The very first entry of the `.plt` section (address `0x400d20` here) is not a
library function at all; it is the linker's lazy-binding trampoline. Recognise it
by its shape (`stp x16, x30, [sp, #-16]!` ... `br x17`). This is *certain*.

**R4 - Phantom (overlapping) functions.**
Compilers align functions to 16 bytes and pad with the instruction `nop`. Ghidra
sometimes mistakes the padding for the start of a tiny function. You detect a
phantom because its body is byte-for-byte identical to a real function that
starts 4 bytes later. Here `0x401b5c` is a phantom of `beacon_seal` (`0x401b60`)
and `0x40205c` is a phantom of `identity_sign` (`0x402060`). This is *certain*
once you compare bodies.

Everything you produce must cite one of R1-R4. "It looks like" is not allowed.

## 33.3 Open the project and take a breath

```bash
open ~/Applications/Ghidra.app     # macOS
~/ghidra/ghidraRun                 # Linux  (Windows: ghidraRun.bat)
```

1. **File → Open Project…** → `ghidra/proj/TelescreenRE.gpr`.
2. Double-click **`teled.stripped`**. The CodeBrowser opens.

The left pane lists the program; the centre is the **Listing** (disassembly);

### The five keystrokes you will use constantly

| key | action | why |
| --- | ------ | --- |
| `G` | **G**o to an address | jump to `0x401000` |
| `F` | decompile the current **F**unction | turn assembly into C |
| `X` | show **X**-references (who calls this / uses this) | build the call graph |
| `L` | rename a **L**abel | give `FUN_00401e00` its real name |
| `;` | add a comment | write your evidence down as you go |

Renaming as you go (`L`) is not cosmetic. It is how you *keep* your understanding
as the program grows. A professional's project is full of names and comments.

## 33.4 Start where the CPU starts

Every program begins at the **entry point**. We know from Volume 32 that it is
`0x401000`:

```bash
readelf -h firmware/teled.stripped | grep Entry
# Entry point address: 0x401000
```

In Ghidra press `G`, type `0x401000`, Enter. You are at `_start`. Decompile it
with `F`. `_start` is generated by the C library; it sets up the runtime and
calls `__libc_start_main`, handing it **`main`** as an argument. So the first
real question is: *what address is passed as `main`?*

Read the listing near `_start` for a load of an address into `x0` just before the
call to `__libc_start_main`. That address is `main`. Here it is `0x400f80`.
Rename it: click `FUN_00400fc0`, press `L`, type `main`.

> **Why this matters.** Every application function is reachable from `main` by
> following calls. `main` is the root of the call-graph tree you are about to
> climb.

## 33.5 Walk the call graph

Press `X` on `main` and you will see it calls three things (by address):

- `aead_init`
- `teled_init`
- `teled_beacon`

These names are meaningless to Ghidra right now, but *you* can read `main`'s
decompilation and see the shape:

```c
aead_init(AEAD_ALGO_AES_256_GCM);
teled_init("SSAT-468547-FEEBD", key);
return teled_beacon(payload) ? 0 : 1;
```

Wait - how did we know those names? Two ways, and both are legitimate:

1. The **string literal** `SSAT-468547-FEEBD` sits in the listing. Ghidra shows
   it as data; `X` on it shows the function that references it (`teled_init`).
2. The three calls appear in a fixed order; the first sets the crypto backend,
   the second initialises the daemon, the third sends a beacon.

So we rename `FUN_00401400` -> `aead_init`, `FUN_00402740` -> `teled_init`, and
`FUN_00402790` -> `teled_beacon`, each backed by the string reference (R1-level
evidence) plus the decompilation.

Now press `X` on `teled_beacon`. It calls `beacon_seal` and `collector_accept`.
Press `X` on `beacon_seal`; it calls `beacon_nonce` and `aead_seal`. Keep going.
In three levels you have the whole spine of the program:

```
main
 |- aead_init
 |- teled_init
 '- teled_beacon
     |- beacon_seal
     |   |- beacon_nonce
     |   '- aead_seal      <- calls EVP_EncryptInit_ex/Update/Final  (R2)
     '- collector_accept
```

That is the entire technique. You begin at the entry point, read the strings and
the imports, and walk outward until every reachable function has a name.

## 33.6 Reading imports to name crypto (the single best trick)

Imports are named even when the binary is stripped. So any function that calls
several `EVP_*` functions is *crypto of a specific kind*. Match the cluster:

| imports a function calls | it is |
| ------------------------ | ----- |
| `EVP_EncryptInit_ex` + `EVP_EncryptUpdate` + `EVP_EncryptFinal_ex` + `EVP_CIPHER_CTX_ctrl` | AEAD **seal** (encrypt + tag) |
| `EVP_DecryptInit_ex` + `EVP_DecryptUpdate` + `EVP_DecryptFinal_ex` | AEAD **open** (decrypt) |
| `EVP_PKEY_new_raw_private_key` + `EVP_PKEY_get_raw_public_key` | **Ed25519/X25519** key derivation |
| `EVP_DigestSignInit` + `EVP_DigestSign` | **Ed25519 sign** |
| `EVP_DigestVerifyInit` + `EVP_DigestVerify` | **Ed25519 verify** |
| `HMAC` + `EVP_sha256` | **HKDF** internals |

The numeric argument `0x43f` (decimal 1087) is the OpenSSL identifier
`NID_ED25519`; `0x40` is a 64-byte Ed25519 signature. These constants are how you
tell X25519 (`NID_X25519`, 0x40f) from Ed25519 (0x43f) at a glance.

This is exactly how we resolved `identity_pubkey`, `identity_sign`,
`identity_verify`, `kex_x25519`, `kex_hkdf`, `aead_seal`, and `aead_open`.

## 33.7 Reading constants to name checksums and formats

Stripped code still contains its constants, and constants are signatures.

- The reflected CRC-32 polynomial `0xEDB88320` (and its bit-reversed table)
  appears inside `crc32_le`, `crc32_uboot`, and `beacon_weak_key`. Search →
  For Strings won't help here; instead use **Search → For Scalar** or read the
  decompiled constant `0xedb88320`. The moment you see it, you are in CRC code.
- Magic numbers name formats: `0x1985` is JFFS2, `0x001b8421` is the vendor
  kernel container, `0xea000000 | offset` is an ARM branch.
- Small readers like `container_magic`, `container_length`, `jffs2_magic`,
  `jffs2_type`, `jffs2_totlen` are one-liners that load a field; they sit next to
  the magic constants that the surrounding code compares against.

This is how we resolved the entire `crc`, `container`, `jffs2`, and `env`
families without a single guess.

## 33.8 Worked example: recovering `beacon_weak_key`

This is the most important function in the course, because it is a **defect**
(a key derived from public data).

1. From §33.5 you already have `teled_beacon` -> `beacon_seal` -> ... Follow the
   call graph until you find a function that calls `crc32_le` in a loop.
2. Press `F` on it. The decompilation shows a loop that feeds the device UID
   (`strlen` for its length) into `crc32_le` once per output byte. That shape -
   *hash the public UID, take the low byte, repeat 32 times* - is a **key
   derivation with no secret input**.
3. Rename it `beacon_weak_key`. The evidence: it is called from the beacon path,
   it takes the UID string, and it fills a 32-byte buffer using only `crc32_le`.
4. Write a comment (`;`): *"DEFECT B6: key = repeated crc32(UID); anyone with the
   UID can compute the key."*

You have just reversed a real cryptographic defect from a stripped binary. The
proof that your name is right is R1: `0x401ae0` is `beacon_weak_key` in the
answer key, and the decompiled behaviour matches exactly.

## 33.10 Special situations you will actually meet

### Identical Code Folding (ICF)

The linker merges functions whose machine code is byte-for-byte identical. Here
`gcm_dec_final` and `chacha_dec_final` share one address (`0x401320`). Two source
names, one function in the binary. You must read the *callers* to know which of
the two names describes the path you are in.

### Phantoms

Covered as rule R4. If a "function" is a single `nop` followed by an identical
twin 4 bytes later, it is padding, not code. Delete it from your mental model.

### Tail calls and `noreturn`

A function ending in `b <other>` (not `bl`) is a **tail call**: it continues into
the other function instead of returning. Ghidra sometimes treats the tail as a
separate function. Confirm with the call graph.

### The dual PLT

Modern toolchains emit two PLT sections, so each import appears twice. Both are
the same library function; do not count them twice.
